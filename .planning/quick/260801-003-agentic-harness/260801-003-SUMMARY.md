# Summary — Quick Task 260801-003

Agent engine built, tested (369 non-slow tests green), and live-verified for
all three query shapes (simple, multi-part, calculation). Five commits:

## What was built

**Foundations** (`09b2c77`): required `harness:` config block —
orchestrator model (gpt-oss-120b, reasoning_effort low), max_hops=4,
max_workers=4; `rag/agent/calculator.py` AST-whitelist evaluator (the LLM
writes expressions, the tool computes — names/attributes/exponent-bombs
rejected); classifier gains `needs_calculation`/`dependent` flags and runs
on the orchestrator model.

**AgentEngine** (`4001196`, `rag/agent/engine.py`): same answer contract as
QueryEngine. classify → concurrent prefetch of every sub-question
(ThreadPoolExecutor; `Retriever.retrieve_with_stats()` pure core + sparse-
stage lock since stanza is not thread-safe) → tool-calling loop ONLY for
calculation/dependent queries (native OpenAI tool calls on TF, verified
live; tools `retrieve` + `calculate`; parallel tool calls; capped hops; any
failure degrades to prefetched evidence) → single synthesis on
generation.model with citation validation. `Answer.trace` records every
step; `tf_client.chat(return_message=True)` surfaces tool_calls.

**CLI** (`452c56e`): `--engine {rag,agent}` on the query CLI — all modes
(single/interactive/batch) work with either engine; `--route` and
`QueryEngine._answer_routed` removed (subsumed); `--category` rejected with
the agent engine.

**Synthesis fixes from live E2E** (`e49f59d`): partial multi-part answers
(fallback sentence + sources block) keep their validated citations — pure
refusals have no sources block per prompt rule 4; CALCULATION_ADDENDUM
explicitly authorizes calculator results as the answer to the arithmetic
part.

## Concurrency (user asked serial-vs-concurrent)

- **Concurrent:** per-sub-question retrievals (embedding is HTTP-bound;
  sparse stage self-serializes on an internal lock; qdrant-local reads and
  CrossEncoder inference are read-safe); multiple tool calls within one
  orchestrator turn.
- **Serial by necessity:** classification (everything routes on it) →
  retrieval; agent hops (N+1 consumes N's results); calculation (after its
  inputs are retrieved); final synthesis (after all evidence).
- Batch-level cross-question parallelism deliberately not built (cost/rate
  profile change).

## Live verification (real index + TF)

- Simple query: fast path (`classify → retrieve → synthesize`, no loop),
  correct 3-year התיישנות answer, 2 valid citations, $0.0026, 59 s local
  (CPU rerank dominates; ~2 s-class on the cloud L40S env).
- Calculation + multi-part query: loop retrieved better evidence, computed
  10000-1500=8500 via the tool, answer uses 8,500 ₪ verbatim, cites the
  התיישנות source, honestly scopes what the sources establish. $0.0144.
- TF native tool calling with gpt-oss-120b verified before building on it.

## Caveats

- Routed `retrieval_stats` remain an element-wise sum across sub-question
  retrievals (documents may double-count).
- `last_stats` is serial-use-only by contract; concurrent callers use
  `retrieve_with_stats`.
- Orchestrator sees evidence truncated to 1500 chars/chunk (spotting
  numbers/gaps, not full pages); synthesis gets full chunks.
