# Summary — Quick Task 260801-001

All three planned tasks executed; 308 non-slow tests green; live-verified
against the real index (retrieve tool + classify subcommand).

## What was built

**T1 — Retriever per-stage public API** (commit `787be29`)
`dense_search` / `sparse_search` / `fuse` / `rerank_candidates` are public
stages with per-call keyword overrides falling back to the config-derived
instance defaults; `retrieve()` is now their composition. Behavior, defaults,
and `last_stats` semantics unchanged (`fuse` fills dense/sparse/fused;
`retrieve` adds gated). 5 new unit tests.

**T2 — CLI stage subcommands** (commit `771b0f6`)
`python -m rag.cli.query {dense|sparse|fuse|rerank|retrieve} "שאלה" --config C`
— dispatched on the first positional arg, classic answer flow untouched.
Flags override the config retrieval params (`--top-k`, `--dense-top-k`,
`--sparse-top-k`, `--rrf-k`, `--gate-threshold`, `--top-n`, `--category`);
one JSON object to stdout (`results` = RetrievedChunk dumps, `stats` for
fuse/retrieve). `rerank --candidates FILE|-` accepts chunk_ids, scored
objects, or a fuse/retrieve envelope; texts hydrated from the dense payload
store (skew warnings on stderr). New `tests/test_query_cli.py` (7 tests).

**T3 — Query classification + --route** (commit `a3f6bb2`)
`rag/classify.py`: one-shot tf_client classifier → self-contained
sub-questions tagged from the closed 12-category list; `mode` and the
top-level category union are derived from validated sub-questions, never
trusted from the LLM; any failure degrades to single/no-filter (never blocks
answering). Exposed as the `classify` subcommand (config-only, no index
load) and as `--route` on the answer flow: retrieve per sub-question
(category filter when exactly one category), pool/dedupe gated chunks by
chunk_id (max rerank kept), ONE generation call with the original question
over the pooled context. `Answer` gains `classification` +
`classification_ms`; classifier cost added to `cost_estimate`; batch records
include the classification. New `tests/test_classify.py` (14 tests).

## Notes / caveats

- Routed `retrieval_stats` are the element-wise SUM over sub-question
  retrievals (documents can double-count across sub-questions) — documented
  in `_answer_routed`.
- A question that is literally just a tool keyword (e.g. `"dense"`) would
  dispatch to the tools parser; quote-irrelevant in practice, documented in
  the module docstring.
- No classifier config block: model defaults to `generation.model`
  (`generation.extra_params` applied only then); `classify --model` overrides.
