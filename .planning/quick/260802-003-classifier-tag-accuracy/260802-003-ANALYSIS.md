# Quick Task 260802-003 — classifier domain-tag accuracy

**Date:** 2026-08-02 · **Sets:** v1 (48) + v2 (121), n=169 · **Cost:** ~$3.5 total

## Result

Production classification moved from 73% correct filters / 18% wrong filters to
**81% correct / 14% wrong** (pooled over both reference sets), plus a JSON bug
fix that was silently discarding 4-12% of all classifications.

| | correct filter | wrong filter | net | no filter |
|---|---|---|---|---|
| before (`baseline`) | 0.728 | 0.183 | 0.544 | 0.089 |
| after (`merged-B`) | **0.805** | **0.136** | **0.669** | 0.059 |

Paired on the same questions: 16 questions gained a correct filter and 3 lost
one (McNemar p=0.0044); 12 wrong filters were fixed and 4 introduced (p=0.077 —
directionally better, not significant on its own). The correct-filter gain is
the statistically solid half of the result; the wrong-filter reduction is real
in direction but n=169 cannot prove it alone.

## What the metric is

The agent filters retrieval for a sub-question **only when it carries exactly
one category** (`rag/agent/engine.py`), so a tag set has three outcomes: exactly
`[gold]` filters to the right slice (**useful**), exactly one wrong tag filters
to the wrong slice (**harmful**), and zero or 2+ tags mean no filter at all.

Ranking on `harmful` alone is degenerate — an arm that tags nothing scores a
perfect 0 and is worthless, which is exactly how `hint-vote` (retrieval majority
vote, no LLM) topped the first sweep's harmful table at 0.077 while abstaining
on 43% of questions. The decision metric is therefore **net = correct − harmful**,
with harmful reported beside it because the two errors are not interchangeable.

## The three findings

### 1. A JSON bug was costing more than any prompt wording

gpt-oss-120b broke its own JSON on 63 of 2028 replies (4% of baseline, up to
12% on some arms), and `_extract_json` dropped every one of them into the
no-filter fallback. Two mechanical defects account for all non-truncated
failures: a duplicated `]` closing `sub_questions` (51x), and Hebrew gershayim
typed as a bare ASCII quote inside a string value (9x, e.g. `בחו"ל`) — a pattern
the production prompt itself modelled in its category list. Qwen3-235B and
DeepSeek-V4-Pro never did either.

This also **confounded the first sweep**: a broken parse scores as a safe
abstention, so the `abstain` arm's apparent edge was mostly its 16 broken JSONs.
Every merge-phase comparison was re-run with the repair active
(commit e241974, recovers 60 of 64 broken spans; the other 4 are truncations).

### 2. Retrieval evidence is the load-bearing improvement

Showing the classifier what an unfiltered hybrid retrieval of the raw question
actually returns (category histogram + 3 snippets, RRF top-10, no reranker) is
worth more than any prompt rewording. In isolation it bought +12 correct filters;
dropping it from the merged arm costs 15 correct filters (p=0.0024).

The leave-one-out ablations show the three components doing different jobs, and
one of them not earning its place:
- **drop the hint** → 15 correct filters lost (p=0.0024). Load-bearing.
- **drop the abstain rule** → 8 wrong filters gained (p=0.0391). It is what stops
  the hint from confidently filtering to the slice the index guessed wrong.
- **drop the decision rules** → 0/4 and 0/−4, p=0.125 on both halves. Honest
  read: the decision rules are not carrying their weight. They ship because they
  are part of the composition that was measured, not because they are proven.

The merge genuinely beats its parts, which was the question this task set out to
settle: `merged-B` > `hint-sparse` (8 wrong filters fixed, 0 introduced,
p=0.0078), > `decision-rules` (p=0.0010 on correct), > `abstain` (p=0.0007).

### 3. Most remaining errors are a taxonomy problem, not a classifier problem

Of `merged-B`'s 23 remaining wrong filters, **16 are within an insurance family**
(property = apartment/mortgage/business; personal-risk = life/personal-accident/
loss-of-working-ability/diseases-disabilities/long-term-care). Cross-family
error is only 4.1% (baseline 7.7%).

`mortgage → apartment` alone is 8 of the 23. Sampling those questions explains
why: v2-104 asks "water leaked from my fridge and damaged the apartment, is that
covered?", v2-106 asks about earthquake damage against an 800,000 ₪ sum insured.
Semantically these *are* apartment questions — they are labelled `mortgage` only
because the source document lives in `corpus/mortgage/` (Harel sells structure
insurance as part of a mortgage package). Every arm, and usually the retrieval
index itself, says apartment. No prompt can recover this; the corpus provenance
is not in the question.

That puts a ceiling on prompt work and points at the real lever: **let the filter
accept a category set** (retrieve across `{apartment, mortgage, business}` when
the query is property-shaped) instead of forcing one string. That would convert
most of the residual 16 into correct group filters. It needs a small retrieval
change (Qdrant `MatchAny`, sparse prefix membership) plus the engine passing a
list, and it is deliberately **not** in this task — it touches the agent engine
that quick task 260802-002 was editing concurrently.

## What was tried

Wide sweep, 12 arms × both sets (`eval_results/classify-sweep-20260802T043108Z/`):
prompt variants (`abstain`, `examples`, `rich-desc`, `decision-rules`), model
swaps (Qwen3-235B, DeepSeek-V4-Pro), `reasoning_effort medium`, 3-sample
self-consistency, a two-stage verify-and-retract pass, index hints, and a no-LLM
retrieval-vote baseline. Merge phase, 13 arms including leave-one-out ablations
(`eval_results/classify-merge-20260802T050208Z/`).

Notable negatives worth not repeating:
- **`examples`** (2 invented example questions per category) was the *worst*
  arm — 0.201 harmful vs 0.172 baseline. Examples anchored the model onto
  surface vocabulary.
- **DeepSeek as classifier** cuts wrong filters (0.130) but loses 23 correct
  ones — it hedges with multi-tags, which the engine reads as "no filter". Also
  3x the latency. Same recipe on DeepSeek (`merged-C`) was not better than on
  gpt-oss.
- **Self-consistency (3 samples)** bought nothing for 3x the cost.
- **`reasoning_effort: medium`** made things slightly worse *and* introduced
  truncations.

## Caveats

- n=169 with ~30 error cases: arm gaps of a few points are noise, which is why
  every claim above carries a paired McNemar count rather than a rate delta.
- The `decision-rules` and hint variants were written after seeing which domain
  pairs the baseline confused, on the same 169 questions used to score them. The
  rules that landed are family-level disambiguation, never question-specific, but
  the measured gain is still an optimistic estimate. A clean read would need the
  v3 reference set (generated in parallel by task 260802-002).
- Hint latency is real: the fuse-only retrieval now runs before classification on
  every agent query. It is the same retrieval that failure mode F2 of the
  260801-004 analysis asked for (the original phrasing never reached the pool),
  but its hits are **not** yet merged into the prefetch pool — doing that is a
  follow-up, and until then the retrieval is paid for twice.
- The landed prompt is byte-identical to the `merged-B` arm and the hint renderer
  is now shared by production and the harness (`tests/test_classify.py` pins
  both), so the sweep numbers carry over. A full live-hint re-run of all 169
  questions against the landed code was **not** done — the live path was smoke-
  tested on single queries only.
