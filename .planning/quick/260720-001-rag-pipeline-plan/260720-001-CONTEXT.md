## Task Boundary

Research and plan (plan-only — no implementation in this task) the RAG ingestion and
query pipelines for the Harel insurance corpus (Exercise 2, Stage 2). Deliverable is
`rag_plan.md` at repo root: an implementation-ready plan covering both pipelines, YAML
configuration, CLIs, and a test strategy (unit tests per phase + E2E system test).

Corpus facts (verified):
- `corpus/` has 12 category directories (apartment, business, car, dental,
  diseases-disabilities, health, life, long-term-care, loss-of-working-ability,
  mortgage, personal-accident, travel), each with `files/` (PDFs) and `pages/` (TXT
  web pages). 1722 files total: 350 PDFs, 221 TXTs (rest are other assets /
  manifest). `corpus/manifest.json` maps relative path → source URL.
- Documents are Hebrew with some English; PDFs contain paragraphs and tables.
- `reference_questions.json`: 48 Hebrew dev questions (8 domains × 6; easy/medium/hard)
  with ground-truth answers and `ground_truth_sources` as `any_of` groups of
  `{file, page}` — citations require file + page metadata.
- Existing: `evalharness/` (LLM-as-judge scoring), `tf_client.py` (Nebius Token
  Factory LLM access, shared key, litellm-based), `contract.py` (FastAPI /ask schema),
  `baseline_answers.jsonl`.

<decisions>
## Implementation Decisions

### Vector DB
- Default: **Qdrant local mode** (embedded, on-disk persistence, no server). Same code
  path must work against a Qdrant server. Chroma and Milvus selectable via config.

### Keyword / BM25 backend
- Default: **in-process BM25** (bm25s or rank_bm25) over Hebrew-normalized tokens —
  zero infrastructure. Elasticsearch/OpenSearch with Hebrew analysis plugin supported
  as config options (Docker), not required for the default path.

### Hebrew NLP normalization
- Default: **Stanza** (Hebrew tokenizer + lemmatizer) behind a normalizer interface.
  Trankit and YAP as alternative implementations of the same interface. Used both at
  ingestion (normalize chunks before keyword indexing) and at query time.

### Scope of this task
- **Plan only.** Research + write `rag_plan.md`. Implementation happens in a follow-up
  task executing that plan.

### Locked stack (from task description)
- LangChain for pipeline orchestration.
- PDF→markdown parsing with Docling (or marker/MinerU if research shows a clear win
  for Hebrew/tables).
- Embeddings: sentence-transformers, bge-m3 default; research Hebrew-tuned
  alternatives on HuggingFace.
- Hybrid retrieval: dense (HNSW) + BM25, with rerankers (bge-reranker / jina-reranker)
  before generation.
- Chunking: multiple strategies — default per-page; also per-paragraph and per-table;
  parameterized size (tokens/bytes where applicable).
- Metadata per chunk: document-name, page-number, category; category filtering at
  retrieval; validation of retrieved chunks before generation.
- YAML config selects module implementations per phase (parser, chunker, embedder,
  vector DB, keyword backend, normalizer, reranker, LLM prompt).
- Two CLIs: ingestion (config → persistent RAG) and query (load RAG, single query or
  interactive loop, independent queries, exit/quit to leave).
- Generation via Token Factory models (tf_client / litellm); multiple prompt variants,
  all requiring citations (file + page) that must appear in the output.
- Unit tests per pipeline phase + end-to-end system test for both pipelines.

### Claude's Discretion
- Exact chunk-size defaults, fusion method (e.g. RRF), top-k values, prompt wording,
  config schema shape, directory layout, and test framework details.

</decisions>

<specifics>
## Specific Ideas

- Retrieval validation step must run before generation (relevance gate via reranker
  scores / category check), and citations in generated answers must be validated
  against retrieved chunk metadata.
- Config should support evaluating different modules in various phases (swap parser /
  embedder / retriever / prompt via YAML) — this feeds the existing evalharness.

</specifics>
