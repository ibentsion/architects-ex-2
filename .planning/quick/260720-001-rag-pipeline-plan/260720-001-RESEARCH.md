## Summary

The locked stack is viable as-is in mid-2026, with two load-bearing caveats. First, **RTL/Hebrew PDF extraction is the single biggest project risk**: every major open-source parser (Docling, marker, MinerU) has documented RTL weaknesses, and AI21 published research showing all modular parsers degrade significantly on Hebrew documents [CITED: ai21.com/blog/rtl-pdf-parsing]. Docling remains the right default (docling-parse gained RtL support in v3.3.0, best table structure, native 1-based page provenance, first-party LangChain integration), but the plan must include an early **extraction-sanity gate** that detects reversed Hebrew before anything else is built. Second, **page provenance is preserved only through the DoclingDocument/JSON path** — exporting to Markdown and chunking the Markdown silently destroys page numbers, which this project cannot afford since citations are graded on `{file, page}`.

For hybrid retrieval, langchain-qdrant's built-in `RetrievalMode.HYBRID` works in local path mode, but its FastEmbed BM25 sparse model **has no Hebrew stemmer** (Hebrew was removed from its supported-language list as a bug fix). This confirms the locked decision: run dense-only Qdrant + a separate in-process **bm25s** index over Stanza lemmas, fused with RRF in our own code. Embeddings: **BAAI/bge-m3** (MIT, 1024-dim, 8192 ctx) is the right default — the BGE-M3 paper specifically shows it stays stable on Hebrew where other multilingual models collapse — with `intfloat/multilingual-e5-large` and the Hebrew-tuned Webiks KolZchut embedder as config-swappable alternatives. Reranker: **BAAI/bge-reranker-v2-m3** (Apache-2.0) as default; jina-reranker-v2 is CC-BY-NC and deprecated. LangChain is on the 1.x line and `langchain-community` is archived — depend only on `langchain-core` + partner packages.

**Primary recommendation:** Docling (DoclingDocument path, never Markdown-intermediate) → HybridChunker + per-page/per-table chunkers → bge-m3 dense in Qdrant local + bm25s over Stanza lemmas + RRF → bge-reranker-v2-m3 gate → tf_client generation. Gate everything behind an early Hebrew-extraction validation step.

## Pipeline Architecture (data flow)

```
INGESTION
corpus/*/files/*.pdf ──► Docling DocumentConverter ──► DoclingDocument (JSON, per-item prov.page_no)
corpus/*/pages/*.txt ──► plain read (no parser; page = null) ─┐
                                                              ▼
                    Chunker (per-page | HybridChunker | per-table) — every chunk carries
                    {file: category-relative path, page: int|null, category, chunk_id}
                          │
          ┌───────────────┴────────────────┐
          ▼                                ▼
  Normalizer (Stanza he lemmas)     Embedder (bge-m3, sentence-transformers)
          │                                │
          ▼                                ▼
  bm25s index (disk, mmap)          Qdrant local (path=..., HNSW, payload=metadata)

QUERY
question ──► [category classifier / optional filter]
   ├─► Embedder ─► Qdrant dense top-k (payload filter: category)
   ├─► Normalizer ─► bm25s top-k
   ▼
 RRF fusion (k=60) ─► bge-reranker-v2-m3 (CrossEncoder) ─► relevance gate (score threshold)
   ├─ pass ─► prompt w/ chunks+metadata ─► tf_client LLM ─► citation validator (file+page ⊆ retrieved)
   └─ fail ─► "I don't have enough information" fallback
```

## Findings by Question

### 1. PDF→Markdown parsing: Docling vs marker vs MinerU

**Recommendation: Docling (v2.113.0), consuming the DoclingDocument object directly — never a Markdown intermediate.**

- **RTL status (the critical axis):** docling-parse added RtL support in v3.3.0, Feb 2025 [CITED: github.com/docling-project/docling-parse CHANGELOG]. However, issue [#1938](https://github.com/docling-project/docling/issues/1938) (Arabic text reversed, Jul 2025) is **still open**, and the older [#455](https://github.com/DS4SD/docling/issues/455) documents jumbled RTL output. AI21's benchmark found **all** modular parsers (explicitly including MinerU and Marker) suffer "significant drop in parsing quality" plus "formatting errors and flagrant hallucinations" on Hebrew documents [CITED: ai21.com/blog/rtl-pdf-parsing]. Conclusion: no parser is a clear win; Docling is least-bad and the Harel PDFs are born-digital (programmatic text, no OCR needed), which is docling-parse's best case. **The plan must include a Wave-0-style extraction sanity check** (see Pitfall 1).
- **marker (1.10.2):** Surya OCR supports Hebrew among 90+ languages, and marker's `TableConverter` is strong; but Surya's own docs say reading order is best-effort, and RTL line order in complex layouts needs postprocessing [CITED: github.com/datalab-to/surya, github.com/datalab-to/marker]. Useful as per-file fallback for PDFs Docling mangles. GPL-3.0 license [ASSUMED].
- **MinerU (3.4.4):** advertises 109-language OCR, but independent 2.5-era testing found Arabic/RTL output "not usable" [CITED: sonusahani.com/blogs/mineru; ai21 blog]. **Rejected.**
- **Page provenance (must-have):** Docling attaches provenance per doc item: `chunk.meta.doc_items[].prov[].page_no`. This survives chunking from a `DoclingDocument` (or its `export_to_dict()` JSON round-trip) but is **destroyed by `export_to_markdown()`** [CITED: github.com/docling-project/docling discussion #1012]. Verified against this repo's ground truth: `reference_questions.json` pages are 1-based ints for PDFs and `null` for TXT files, and `file` is the category-relative path (e.g. `apartment/files/הודעה-על-תקופת-התיישנות.pdf`) [VERIFIED: local inspection]. Docling `page_no` is 1-based [ASSUMED — confirm on first parsed doc against a known ground-truth page].
- **LangChain integration:** `langchain-docling` 2.0.0 provides `DoclingLoader` with `ExportType.DOC_CHUNKS` (each chunk → one LC `Document`), a pluggable `chunker` (default `HybridChunker`), and a pluggable `meta_extractor` (`BaseMetaExtractor.extract_chunk_meta`) to surface `{file, page, category}` into `Document.metadata` [CITED: docs.langchain.com + github.com/docling-project/docling-langchain]. **HybridChunker** = hierarchical document-structure chunking + tokenizer-aware split/merge (`HybridChunker(tokenizer=EMBED_MODEL_ID)`, `merge_peers=True`) [CITED: docling-project.github.io/docling/concepts/chunking]. This maps cleanly onto the locked "per-paragraph" strategy; "per-page" and "per-table" chunkers are simple custom iterations over `DoclingDocument` items grouped by `prov.page_no` / `TableItem`.
- **Ingestion cost:** Docling layout+table models on CPU are the slow path — budget hours, not minutes, for 350 PDFs on CPU; persist parsed `DoclingDocument` JSON per file so re-chunking never re-parses [ASSUMED: throughput from training knowledge — measure on a 10-doc sample].
- **TXT web pages:** no parser — read UTF-8, chunk by paragraphs/size, `page: null` (matches ground truth), keep `manifest.json` URL as extra metadata.

### 3. Hybrid retrieval architecture

**Recommendation: Architecture B — dense-only Qdrant local + separate bm25s index + RRF in our code.** (This also matches the locked "in-process BM25" decision.)

- **What langchain-qdrant offers:** `QdrantVectorStore` with `RetrievalMode.HYBRID` (requires Qdrant ≥1.10 Query API), works in **local path mode** (`QdrantClient(path=...)`) with named dense + sparse vectors and payload filtering (`models.Filter`/`FieldCondition` — filterable HNSW, so `category` filtering is efficient) [CITED: docs.langchain.com/oss/python/integrations/vectorstores/qdrant]. Local mode caveat: the path is locked to a single process — ingestion CLI and query CLI cannot hold it simultaneously.
- **Why not its built-in hybrid:** the sparse side is `FastEmbedSparse(model_name="Qdrant/bm25")`, whose stemmer list **does not include Hebrew** — Hebrew was in an older list by mistake and was removed in the fix ("fix list of supported languages in bm25"); Snowball simply has no Hebrew stemmer [CITED: github.com/qdrant/fastembed issue #505 + fastembed/sparse/bm25.py]. Workaround (`disable_stemmer=True` + feeding pre-lemmatized text) requires a custom `SparseEmbeddings` implementation anyway, at which point the in-process BM25 is simpler and identically capable.
- **BM25 library: `bm25s` 0.3.9**, not `rank_bm25` 0.2.2. bm25s is actively maintained (2026 releases), scipy-sparse eager scoring (~7x–500x faster queries), supports passing **pre-tokenized token lists** (perfect for Stanza lemmas), and persists via memory-mapped on-disk indexes [CITED: huggingface.co/blog/xhluca/bm25s; github.com/xhluca/bm25s]. rank_bm25 has had no release since ~2022 [CITED: PyPI].
- **Fusion:** RRF with k=60 (standard constant), implemented in our retriever module (~15 lines). Category filtering: Qdrant payload filter on the dense side; on the BM25 side retrieve a larger k and post-filter by chunk metadata (corpus is small — 350 PDFs + 221 TXT — so this is cheap). Keep a single chunk-id namespace so fusion joins on ids.
- **Server migration path:** identical `QdrantVectorStore` code with `url=` instead of `path=` — satisfies the locked "same code path against a server" requirement. Optional future upgrade (documented, not planned): custom `SparseEmbeddings` emitting Stanza-lemma term frequencies with Qdrant's server-side `Modifier.IDF` to move BM25 into Qdrant when a server exists.

### 4. Hebrew normalization with Stanza

- **Pipeline:** `stanza.Pipeline('he', processors='tokenize,mwt,pos,lemma')` (stanza 1.14.0). Hebrew **does** use the MWT processor: fused tokens like בבית are expanded into syntactic words (ב + בית) — visible in the performance table where Hebrew "Words" (92.29) diverges from "Tokens" (99.98) [VERIFIED: stanfordnlp.github.io/stanza/performance.html, v1.5.1/UD 2.12 numbers]. Lemmatizing the expanded words strips the prefixed prepositions/articles (ו/ב/ל/כ/מ/ש/ה), which is exactly what makes BM25 work in Hebrew — surface forms of the same noun otherwise fragment across prefix combinations.
- **Model choice:** default package is HTB (news-domain): words 92.29 / UPOS 89.99 / lemmas 89.71. The `iahltwiki` package scores better on modern text: words 94.61 / lemmas 92.51 [VERIFIED: same page]. Recommend making the stanza package a config key with `iahltwiki` worth an eval run.
- **Indexing recipe:** index the **union of lemma + surface form** per token (hedges against the ~8–10% lemma error rate on domain terms like ביטוח-specific vocabulary); lowercase Latin tokens; strip nikud/punctuation. Apply the identical normalizer to queries.
- **Performance:** CPU throughput unmeasured here; expect the pos+lemma stack to be the bottleneck at roughly hundreds of sentences/sec on CPU [ASSUMED — measure on sample; use `nlp.bulk_process`/batched documents at ingestion]. For 571 documents this is minutes-to-tens-of-minutes, acceptable for an offline ingestion CLI; query-time normalization of one question is negligible.
- **Pitfalls:** (a) MWT expansion changes token counts — never mix normalized token offsets with display text offsets; keep normalized text solely for the BM25 index and always store/display the original chunk text. (b) Stanza downloads models on first run (`stanza.download('he')`) — the ingestion CLI must handle/document this. (c) Proper nouns (הראל) can be mis-lemmatized — the lemma+surface union covers this.
- **Alternatives behind the same interface:** `trankit` (XLM-R-based UD pipeline, same processor semantics, often better accuracy but heavier) and YAP (Go binary, Hebrew-specific morphological disambiguation, awkward to embed — HTTP subprocess) [ASSUMED: training knowledge, both stale-risk — verify only if actually implementing those adapters].

## Common Pitfalls

1. **Reversed Hebrew from PDF extraction (highest risk).** Docling's RTL fix is partial (issue #1938 open). *Mitigation for the plan:* a mandatory early validation step — parse 5–10 PDFs spanning categories, assert canary words (e.g. ביטוח, הראל, פוליסה) appear in output and their reversals (חוטיב…) do not; also spot-check a ground-truth `{file, page}` pair contains the expected fact. If a file fails: try marker fallback, or a line-level BiDi repair pass; if systemic: escalate before building anything downstream.
2. **Page numbers lost via Markdown export.** Chunk from the `DoclingDocument` (or `export_to_dict()` JSON), never from exported Markdown [CITED: docling discussion #1012]. Unit test: every PDF chunk has `page ≥ 1`; every TXT chunk has `page = null`.
3. **Citation format mismatch.** Ground truth uses **category-relative paths with Hebrew filenames** (`apartment/files/חוברת-....pdf`) and `page: null` for TXT [VERIFIED: local reference_questions.json]. Chunk metadata `file` must store exactly this relative path (POSIX separators, NFC-normalized Unicode — macOS/other tools can produce NFD; assert NFC at ingestion). Filenames contain hyphens and underscores but the dev-set files show no nikud [VERIFIED: local ls]; still normalize NFC defensively.
4. **Chunk size vs tables.** Page-sized chunks dilute dense embeddings and blow the e5 512-token window; sentence-sized chunks orphan table cells from headers. Keep **tables atomic** (one chunk per table, serialized as Markdown, with heading context), default text chunks ~300–512 tokens via HybridChunker with the embedder's tokenizer, and per-page chunks as the config default for citation simplicity (bge-m3's 8192 window tolerates full pages).
5. **Mixed Hebrew/English BM25.** Corpus and questions mix scripts (e.g. dental claim form "dental-claim-form"). The normalizer must keep Latin tokens (lowercased), not strip them; numbers (₪ amounts, percentages, waiting periods) are high-value BM25 tokens — keep digits, normalize ״/ geresh/gershayim quotes and maqaf (־) to plain forms.
6. **e5 prefix omission.** If `multilingual-e5-large` is selected via config, `query: `/`passage: ` prefixes are mandatory — bake prefix handling into the embedder adapter, not call sites.
7. **Qdrant local single-process lock.** Ingestion and interactive query CLIs cannot open the same path concurrently — document this; it also means the E2E test must run pipelines sequentially.
8. **Ingestion re-parse cost.** Cache parsed DoclingDocument JSON per source file (keyed by content hash) so chunker/embedder experiments don't re-run the expensive parse.
