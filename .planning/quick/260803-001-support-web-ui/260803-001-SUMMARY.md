## Post-review fixes (found by the coordinator's live runtime testing)

Both were real, both were things the unit tests could not have caught because
they were wrong *assumptions* rather than wrong code, and the tests encoded the
same assumptions.

### R1 — the graded submission rendered with no questions (`9a54703`)

`blind_questions.json` (390 questions, fetched from the artifacts dataset, not
in git) is the **only** source that names the ids in `team_1_results.jsonl` —
the actual graded submission and the most useful dataset in the History view.
It was missing from `QUESTION_SOURCES`, so all 390 pairs rendered
`question: null`.

Verified before changing anything: blind ids are `int-*`, dev sets are
`dev-*`/`v2-*`/`v3-*` — **0 collisions**, and blind covers **390/390** of
`team_1_results.jsonl` (nothing else covers any of it). Discovery already
tolerated a missing source (`if not path.is_file(): continue`); that is now
covered by a test and stated in the comment, since this source is absent on a
fresh clone. Real result: `390 pairs, 0 without a question`.

### R2 — `content_preview` was null for essentially every citation (`2c40d1b`)

`preview_text()` returned None for anything not `.txt`, with the rationale
"a PDF page's text would mean re-running the ingest parser on a UI request".
The coordinator is right that this is wrong for this repo:
`evalharness.pages.PageStore` already maps `{file, page}` → page text through
corpus walk → sha256 → **Docling parse cache** (316 entries present), which is
the same resolution the citation judge uses — so the card shows the text the
retriever actually indexed, and nothing is parsed on a request.

Measured before building on it: PageStore resolved **40/40** real
`team_1_results.jsonl` citations, 3.0 s for the first call (corpus walk),
0.00 ms memoized.

- One module-level PageStore per repo root, built on first use and kept for the
  process. `threading.Lock` guards both construction *and* lookup, because the
  store memoizes into plain dicts and uvicorn runs sync endpoints on a thread
  pool.
- `_resolve_preview` now takes the page number — it previously dropped it, and
  a preview of the wrong page is worse than none.
- **Import direction:** `webapi → evalharness → rag`. Clean, and no new
  dependency: `evalharness` is first-party and in-repo, `evalharness/__init__.py`
  is a docstring only, and `pages.py` imports nothing but stdlib at module
  level. `evalharness` does not import `webapi`, so there is no cycle. Nothing
  was added to `requirements.txt`.
- Degradation contract preserved and tested: missing `corpus/`, missing
  parse-cache entry, unknown file, out-of-range page, page-less paged citation,
  and an exploding store all yield `None` — never a 500, never an exception out
  of `_citations`. Traversal still goes through `resolve_in_repo` first.
- `quote` → page text → nothing precedence unchanged.

**Scope note (please review):** I also fixed the *same stale rationale at its
second call site*. `/api/citation/content` returned `text: null` for PDFs with
that identical comment; it now serves the cached page text, and
`CitationSidebar` shows it beside the page image instead of only when there is
no image. This is one gap with two call sites rather than new scope — but it
is the one change here you did not explicitly ask for.

### R3 — three divergences from the supplied product spec (`303ebee`)

1. **Persistent nav rail.** The spec's App Layout calls for a persistent left
   sidebar for page navigation; it had been built as a horizontal tab strip in
   a top header. Now a vertical rail (icon + label + active state) on the
   inline-start edge — the right, under RTL — with the product mark inside it,
   so there is no header bar. Each view keeps its own split.
2. **40×55 thumbnail on every citation card.** The page image previously
   appeared only in the expanded detail pane. Card and detail now share one
   `PageThumbnail` component, and therefore one failure policy: a 404 render
   falls back to a placeholder box and the component stops rendering an
   `<img>`, so a failure cannot loop. `loading="lazy"` keeps an off-screen card
   list from firing every cold render at once.
3. **Citation-panel skeletons.** `CitationSidebar` takes a `loading` prop
   (`busy` in the live view, the dataset load in history) and skeletons its
   card list; `CitationDetail` skeletons while `/api/citation/content` is in
   flight — a real wait on a cold corpus walk, not a theoretical one.
   The detail slide-in also now transitions opacity as well as transform
   (`transition-all`), which is the "smooth slide-in" the spec asks for; the
   panel itself is always mounted, so animating it further would have meant
   contorting the layout and was skipped.

**A latent 500 that fix 2 exposed.** One thumbnail per card made concurrent
cold renders the normal case rather than a rarity, and a burst against the real
corpus failed with `PdfiumError: Data format error`. Isolating it before
fixing: **0 failures single-threaded, ~2 of 71 under 12-way concurrency** — so
PDFium's thread-unsafety, not a corrupt document. Three changes:

- The render is serialized (`_render_lock`). Cache hits never take the lock,
  and the lock is double-checked inside so a waiting thread serves the file the
  first one just wrote.
- `PdfiumError` → `CorpusUnavailable` → 404. A genuinely corrupt PDF is a
  placeholder, which is what the module's degradation contract already
  promised and did not deliver.
- Write-then-rename. A half-written JPEG would have been cached forever and
  served as a broken image on every later request — and the frontend's
  no-retry policy would have shown a placeholder permanently.

Real cold burst, 71 unique pages, 12 concurrent, cache cleared first:
**71 × 200 in 2.0 s**; warm 0.36 s; 71 cached JPEGs, 0 stray temp files.

  step   0.41s                  step   0.47s

## Deviations from plan

### Auto-fixed issues

**1. [Rule 1 - Bug] SSE stream stalled 15 s after the last step**
- **Found during:** Task 3, when the stubbed-engine tests took 79 s instead of ~4 s.
- **Issue:** The drain loop was `while not (task.done() and events.empty())` with
  `asyncio.wait_for(events.get(), timeout=HEARTBEAT_SECONDS)`. After the final
  step is consumed the queue is empty and the engine future may not yet be
  marked done, so the loop waited out a **full 15 s heartbeat** before emitting
  the answer. Every real query would have carried 15 s of dead air.
- **Fix:** Race the next record against the completion future with
  `asyncio.wait(..., return_when=FIRST_COMPLETED)`, records checked first, then
  a final `get_nowait()` drain for anything queued in the last instant.
- **Files:** `webapi/agent_app.py`. **Commit:** `428bb0e`.
- The plan's Task-3 verify (`ast.parse`) could not have caught this.

**2. [Rule 1 - Bug] Traversal on a non-PDF returned 404 instead of 400**
- **Found during:** Task 5, by its own test.
- **Issue:** `page_thumbnail` checked the `.pdf` suffix *before* resolving the
  path, so `file=../../etc/passwd` fell out as `CorpusUnavailable` (404). Still
  rejected, but it reported the wrong thing and put a file-type check ahead of a
  security check.
- **Fix:** `resolve_in_repo` first, always; suffix/cache/existence after.
- **Files:** `webapi/corpus_view.py`. **Commit:** `429d379`.

**3. [Rule 1 - Bug] `or` would have swallowed a zero cost**
- **Issue:** The plan specified `cost_usd = record.get("cost_usd") or
  record.get("cost_estimate")` and the same shape for `domain`. With `or`, a
  real measured `0.0` cost or `0.0` confidence becomes `None`.
- **Fix:** A `_first()` helper testing `is not None`, with a test
  (`test_record_to_pair_keeps_a_zero_cost_instead_of_dropping_it`).
- **Files:** `webapi/schema.py`. **Commit:** `b2ad9e8`.

### Deliberate deviations

**4. `tests/test_webapi_agent_app.py` added (not in the plan's file list)**
The plan gated Task 3 on `ast.parse` alone. The execution brief required
verifying the SSE app "by import + a stubbed/fake engine". Added 8 tests
(framing, event order, Hebrew unescaped, error frame, heartbeat, empty-question
rejection, no `/ask`, engine built once and released). This is what surfaced
deviation 1.

**5. Frontend scaffolded by hand instead of `npm create vite@latest`**
`create-vite` crashes on this box: `SyntaxError: The requested module
'node:util' does not provide an export named 'styleText'`. `styleText` landed in
Node 21.7; this machine runs **21.6.2**. Vite 6/7 declare the same engine range
(`^20.19.0 || >=22.12.0`). So `package.json`/`tsconfig`/`vite.config.ts` are
hand-written and **Vite is pinned to 5.x**, which supports Node 21. Noted in
`webui/package.json`. Same output, no interactive scaffold.

**6. Answer-file glob widened `rag_answers_*.jsonl` -> `rag_answers*.jsonl`**
The repo contains `rag_answers.jsonl` (no underscore), which the plan's glob
misses. It is also the file two `metrics.json` records name as their
`answers_file`, so the narrower glob would have silently degraded those judged
runs to judgments-only.

**7. `load_pairs` owns the dataset allowlist**
The plan put unknown-dataset rejection in the bridge. It lives in
`webapi/datasets.py` instead (raising `UnknownDataset`), so the check cannot be
forgotten by a future caller. The bridge still maps it to 400. `resolve_in_repo`
runs *before* the allowlist, so traversal reports `PathEscape`.

**8. Identity assertion relaxed to equality at the `Answer` boundary**
The plan's Task-1 behavior said the sink gets "the same dict object that lands
in `answer.trace`". Pydantic validates-and-copies dicts when constructing
`Answer`, so identity cannot hold there. Identity IS asserted where it is
actually true — at `_emit` (`test_emit_hands_the_sink_the_very_dict_it_appends`), which
is what makes the read-only warning in the docstring meaningful — and equality
is asserted against `answer.trace`.

**9. `_run_meta` / verified-facts correction**
The plan's verified facts said `reference_questions.json` and `_v2` are
`{"questions": [...]}`-wrapped and only `_v3` is a bare list. In fact **all
three are bare JSON lists**. The loader handles both shapes either way, so no
behavior changed; the regression-guard test asserts 186 ids across the three
files with 0 pairwise collisions.
